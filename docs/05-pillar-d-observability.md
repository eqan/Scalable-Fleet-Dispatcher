# 05 — Pillar D: Observability Primitives & Health Monitoring

> Load when: provisioning in-cluster monitoring or building operational dashboards.
> Prereqs:   `02-pillar-a-kubernetes.md` (targets to scrape); `00-overview.md`
> Status:    DONE ✅

## Objective (from the brief)

Full operational visibility:
- **Telemetry & metrics sinks**: a localized monitoring pipeline (Prometheus + Grafana or equivalent).
- **Operational health visualization**: a dashboard showing **pod restarts, error-log spikes,
  cluster capacity limits, and external service dependency response metrics**.

## Reuse what exists (don't rebuild from zero)

The repo already ships monitoring assets under `packages/monitoring/` — **port these into K8s**:
- `grafana/provisioning/` — datasources + the "API Overview" dashboard (5 panels).
- `prometheus/prometheus.yml` — scrape config (currently targets `api:4000`).
- `loki/` + `promtail/` — log aggregation configs.

The api already exposes app metrics: `prom-client` middleware emits `http_request_duration_ms`
(labels: `method`, `route`, `status_code`) at **`/metrics`** (mounted outside `/api`, so it must
stay cluster-internal — see the negative smoke test in `04-*`).

## Decision

**Chosen: a separate `monitoring` Helm release with `kube-prometheus-stack` + Loki + Promtail.**
Rationale: it bundles Prometheus Operator, node-exporter, kube-state-metrics, and Grafana with sane
defaults, so you get **cluster** signals (restarts, capacity) for free and only add app-specific
pieces.

The release now lives under `infra/helm/monitoring` and is installed by `run-platform.sh deps`
into the `monitoring` namespace. Grafana is exposed at `https://grafana.dispatch.localtest.me`, while
the API `/metrics` endpoint remains cluster-internal and is scraped through a `ServiceMonitor`.

> Either is acceptable per the brief ("comfortable stripping Prometheus out for your own"). Pick one,
> justify it in the matrix.

## Wiring in-cluster

- **Scrape the api**: `infra/helm/monitoring/templates/api-servicemonitor.yaml` targets the
  `dispatch-api` Service on `/metrics`. `/metrics` stays on a ClusterIP only and is never routed through
  the app Ingress.
- **Cluster metrics**: kube-state-metrics and node-exporter come from `kube-prometheus-stack`.
- **Logs**: Promtail ships Kubernetes pod logs to Loki. The repo now also includes a Kubernetes log
  discovery reference config at `packages/monitoring/promtail/promtail-k8s-config.yml`.
- **Grafana provisioning**: datasources and dashboard JSON are applied from
  `packages/monitoring/grafana/provisioning/` as labeled ConfigMaps, so Grafana auto-loads them with
  zero manual setup.
- **Grafana access**: a separate ingress host `grafana.dispatch.localtest.me` is fronted by its own
  self-signed TLS secret and admin secret generated by `run-platform.sh`.

## Required dashboard panels (map to the brief)

| Panel | Signal | Source |
|-------|--------|--------|
| **Pod restarts** | `kube_pod_container_status_restarts_total` (rate/increase) | kube-state-metrics |
| **Error-log spikes** | `count_over_time({app="dispatch-api"} | json | level="error" [5m])` | Loki |
| **API 5xx error rate** | `rate(http_request_duration_ms_count{status_code=~"5.."}[$__rate_interval])` by route | api `/metrics` |
| **Cluster capacity limits** | CPU/mem usage vs requests/limits per pod; node allocatable headroom | node-exporter + KSM |
| **Dependency response metrics** | api→redis / api→mongo latency; probe/health latency | `/api/health` latency, request histogram |
| **Request duration heatmap** | `sum(rate(http_request_duration_ms_bucket[$__rate_interval])) by (le)` | api `/metrics` |

> "External service dependency response metrics": the app's `/api/health` already returns
> `latency_ms` for redis and mongo. Optionally add a small gauge/histogram in api for dependency
> latency to graph it directly — a clean, low-risk backend addition.

That optional metric is now implemented as `dispatch_dependency_latency_ms{service}` and
`dispatch_dependency_up{service}`, updated on every `/api/health` call (no extra `status` label —
keeps cardinality flat; up/down is the separate gauge).

## What was added

- `infra/helm/monitoring` — dedicated monitoring chart with upstream dependencies:
  - `kube-prometheus-stack`
  - `loki`
  - `promtail`
- `infra/helm/monitoring/templates/api-servicemonitor.yaml` — Prometheus Operator scrape wiring for
  the API
- `packages/monitoring/grafana/k8s/datasources.yaml` — in-cluster datasource URLs
  (kept outside `provisioning/datasources/` so Compose Grafana does not load it and crash on
  duplicate default Prometheus entries)
- `packages/monitoring/grafana/provisioning/dashboards/platform-observability.json` — Kubernetes
  dashboard covering restarts, log spikes, 5xx rate, capacity, dependency latency, and request heatmap
- `packages/monitoring/promtail/promtail-k8s-config.yml` — Kubernetes pod log discovery reference
- `tests/infra/test_monitoring.py` — monitoring-focused validation for workload readiness, Grafana
  ingress, ServiceMonitor presence, Prometheus scrape health, and Grafana provisioning ConfigMaps

## Definition of done

- Prometheus scrapes the api + cluster; targets are **UP**.
- Grafana auto-provisions the datasources + dashboard; all six panel types are represented.
- Loki receives Kubernetes pod logs with `app="dispatch-api"`-style labels suitable for LogQL.
- `run-platform.sh deps` installs the monitoring stack, and the infra suite validates the core wiring.
- Access coordinates (URL, generated creds file, and validation flow) are documented in the runbook.
